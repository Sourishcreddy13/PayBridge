## 3. Problem Statement & Expected Solution

### 3.1 Problem
A bank wants to consolidate its multiple payment rails (UPI, NEFT, RTGS, IMPS) behind a single hub that handles routing, idempotency, reconciliation, refunds, and daily settlement. You build this hub — under one constraint: no manual coding. All external rails are stubbed adapters with configurable success/failure responses; every line of production code must be generated by Claude Code agents under your supervision.

### 3.2 Your Role
AI-Native Engineer — architect, supervisor, and quality gatekeeper. You write specifications, configure agents, install guardrails, and review pull requests. You do not write production code by hand.

### 3.3 Expected Solution
A working platform delivered as a Git repository that demonstrates:
* A complete AI-native engineering substrate built on the Claude Harness Engine plugin foundation, extended with payments-operations-specific specs, agents, skills, hooks, commands, and MCP integration.
* A functional payments hub built end-to-end by Claude Code agents — covering rail routing, idempotency, retry handling, reconciliation, refund flows, and daily settlement file generation — with no hand-written production code.
* An evidence trail (PRs, agent logs, post-mortems, sprint contracts) proving the work was agent-led.

### 3.4 Applicable Rules
* **No-Hand-Coding Rule.** All production code, tests, and migrations must be generated by Claude Code agents. Hand-edits are limited to specs, CLAUDE.md, agent definitions, hooks, skills, and other substrate files.
* **Spec-Is-Truth Rule.** Whenever a spec and code disagree, the spec wins. Update the spec deliberately and regenerate the code.
* **PR-Only Merge Rule.** No direct commits to main. All changes flow through agent-reviewed pull requests.
* **Synthetic-Data Rule.** Use only dummy data. Do not use Virtusa confidential or customer-sensitive data for this project.

## 5. Acceptance Criteria & Non-Functional Requirements

### 5.1 Functional Acceptance Criteria

| ID | Criterion |
| :--- | :--- |
| **AC-01** | Customer can initiate a payment with beneficiary, amount, and narration; the system assigns a `payment_id` and accepts an `idempotency_key`; the initial state is `PENDING`. |
| **AC-02** | Idempotency rule: re-submitting the same `idempotency_key` returns the original `payment_id` without creating a duplicate payment record. |
| **AC-03** | Routing engine selects the rail based on amount and beneficiary type (e.g., RTGS for amounts $\ge \text{₹}2,00,000$; UPI for retail amounts $\le \text{₹}1,00,000$; NEFT otherwise); the routing decision is logged with reason. |
| **AC-04** | Payment lifecycle states `PENDING` $\rightarrow$ `PROCESSING` $\rightarrow$ `SETTLED` / `FAILED` / `REFUNDED` are enforced; invalid transitions raise `InvalidPaymentStateException`. |
| **AC-05** | When the stubbed rail adapter returns a transient failure, the payment is retried per the configured retry policy; permanent failures move the payment to `FAILED` with a reason code. |
| **AC-06** | Reconciliation matches outbound payment records against inbound settlement-file entries; unmatched entries are flagged in an exception report for ops review. |
| **AC-07** | Daily settlement file is generated for all `SETTLED` payments of the day with matched / unmatched indicators; the generated file is append-only and immutable once written. |
| **AC-08** | Customer can request a refund on a `SETTLED` payment; the refund creates a new reverse entry linked to the original; the original payment status moves to `REFUNDED`. |
| **AC-09** | All state transitions and routing decisions are persisted as an immutable audit record with timestamp and actor. |
| **AC-10** | Ops admin can view daily volumes by rail and status, the unmatched-entries queue, and the refund queue. |

*Note: Each AC must have at least one test referencing its AC-NN identifier.*

### 5.2 Non-Functional Requirements

| ID | Requirement |
| :--- | :--- |
| **NFR-01** | Amount, fees, and refund values are computed in fixed-point (`BigDecimal` / `decimal`) — never floating-point. |
| **NFR-02** | Payment records, state transitions, settlement entries, and refund records are all append-only. |
| **NFR-03** | Beneficiary account numbers, IFSC codes, and payer details are masked in logs and never persisted in plaintext where avoidable. |
| **NFR-04** | Authentication boundary at controller layer; customer / ops / admin roles are separated. |
| **NFR-05** | Database migrations are append-only. |
| **NFR-06** | Structured JSON logs with request correlation IDs and `payment_id`. |
| **NFR-07** | Health endpoint returns 200 within 1 second of a successful startup. |
| **NFR-08** | Architecture rules enforced as tests — duplicate payments for the same `idempotency_key` cannot be created; `SETTLED` payments cannot be mutated except via a `REFUNDED` transition. |

## 6. Functional Scope

### 6.1 Customer / End-User Functionality (User Journeys)
* **Initiate Payment.** Submit beneficiary, amount, and narration; receive a `payment_id` and an `idempotency_key` handshake.
* **Track Status.** View the payment lifecycle (`PENDING` $\rightarrow$ `PROCESSING` $\rightarrow$ `SETTLED` / `FAILED` / `REFUNDED`) and reason codes.
* **Request Refund.** Raise a refund on a `SETTLED` payment; track the reverse entry and refund status.
* **Payment History.** View past payments with timeline, rail used, and final status.

### 6.2 Internal & System Functionality
* **Routing Engine.** Rules-based rail selection (UPI / NEFT / RTGS / IMPS) by amount, currency, and beneficiary type.
* **Rail Adapters (stubbed).** Configurable adapters per rail with deterministic success / failure / transient-error responses for testing.
* **Idempotency Manager.** Enforces unique payment creation per `idempotency_key` across retries and duplicate submissions.
* **Retry & Backoff.** Configurable retry policy for transient failures; permanent failures are surfaced to ops.
* **Reconciliation Module.** Matches outbound payments against inbound settlement-file entries; surfaces unmatched items.
* **Settlement File Generator.** Daily batch job producing the append-only settlement file with matched / unmatched indicators.
* **Refund Engine.** Generates reverse entries linked to original payments; transitions states with audit.
* **Ops Dashboard.** Payment volumes by rail and status, unmatched queue, refund queue, retry pipeline.

### 6.3 Out of Scope
You do not need to build:
* Real UPI / NEFT / RTGS / IMPS network connections — all rails are stubbed adapters.
* Real bank-to-bank messaging (SWIFT, etc.) — cut of scope entirely.
* Real clearing-house / RBI settlement infrastructure.
* Real beneficiary verification or KYC checks (stub a flag).
* Foreign-exchange or international remittances.
* Production deployment, secret management, multi-region, distributed locking.

## 7. AI-Native Implementation Expectations

The harness ships 7 base agents (planner, generator, evaluator, security-reviewer, test-engineer, design-critic, ui-designer), 12+ hooks, base commands, sprint contracts, an evaluator wired to Playwright MCP, and a self-healing loop. On top of that foundation, your repository must add the project-specific substrate listed in this section. The rubric scores the final repository — both Harness-supplied and learner-added artifacts contribute, but the thresholds below are calibrated so that learners who only install Harness without customizing for the project domain will not meet them.

* `specs/app_spec.md` (root spec) and `specs/<feature>_spec.md` per major feature, each with explicit Acceptance Criteria sections.
* Layered `CLAUDE.md` — root + per-module + per-folder; `AGENTS.md` as a table of contents only.
* At least 3 project-specific skills under `.claude/skills/` added by you (examples: routing-rule-evaluator, idempotency-key-generator, reconciliation-matcher, settlement-file-builder, retry-policy-evaluator; or technical: state-machine-validator, archtest-author, audit-tracer).
* At least 2 project-specific custom commands under `.claude/commands/` added by you (beyond Harness defaults).

These may be **domain agents** (e.g., routing-agent, reconciliation-agent, refund-agent, settlement-file-agent), **technical agents** that strengthen the engineering substrate (e.g., state-machine-validator-agent, idempotency-validator-agent, archtest-author-agent), or a mix of both. ### 7.2 Business Understanding (20 marks)
